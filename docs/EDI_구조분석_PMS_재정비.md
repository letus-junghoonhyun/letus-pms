# EDI 구조 분석 · PMS 재정비 · AJ 요청 정리

작성: 2026-10-23 · 근거: EDI 8개 메뉴 화면·코드 직접 확인(읽기 전용, 14C·18F 계정), 동기화 데이터(9/26~10/23 이동 5,229건, 납품요청 44건)

---

## 1. 결론 먼저

1. **수불의 기준은 EDI, 입력·확인·대사는 PMS**로 역할을 나누면 제대로 된 수불관리가 가능해요. EDI는 AJ 정산의 원장이라 바꿀 수 없고, PMS는 EDI가 못 하는 것(현장 확인·사진·수량 차이·요청 추적·마감 점검)을 채워요.
2. **EDI의 입고확인이 거의 안 쓰이고 있어요.** 9/26 이후 이동 5,229건 중 입고확인 368건(7%), 미확인 93%. 받는 쪽 확인이 없으니 "보냈다고 등록한 수량"이 그대로 재고가 돼요. 센터 가짜 재고(약 58,000장)의 직접 원인 중 하나예요.
3. **AJ 공급(렌탈입고)은 요청 1건이 여러 번·여러 AJ센터에서 나눠 들어와요.** 예) 시디즈평택 18F: 전주 14 + 경기광주 20. EDI에는 납품요청 코드와 렌탈입고를 잇는 값이 없어서 "요청 대비 얼마 들어왔는지"를 정확히 알 수 없어요. → AJ 요청 1순위.
4. **EDI는 사람이 화면에서 누르는 구조**라 완전 자동은 어렵지만, PMS가 값을 만들고 스크립트가 화면을 채우고 사람이 [저장]만 누르는 방식(지금 구현한 방식)으로 손입력은 거의 없앨 수 있어요.
5. PMS는 지금 **옛 구조(장부·협력업체 확인)와 새 구조(EDI 기준)가 섞여 있어요.** 메뉴를 업무 흐름 기준으로 재정비할 때가 됐어요.

## 2. 우리 업무 흐름 (목표 그림)

```
[AJ] ──납품요청──▶ [AJ센터] ──렌탈입고──▶ [우리 센터 / 현장]
                                              │
                          출고(센터→시공팀·업체) │ 작업장 간 이동 │ 반납(현장→센터)
                                              ▼
                                       [시공팀·업체·현장]
                                              │
                               회수(우리→AJ센터, 반납출고) ──▶ [AJ]
```

| 단계 | 누가 | 어디서 등록 | EDI 기록 | PMS 역할 |
|---|---|---|---|---|
| ① 공급 요청 | 우리 | PMS AJ 요청 → EDI 납품요청(채우기·등록) | 납품요청(요청코드 C…) | 요청 관리, 마감 16시·기준수량, 상태 추적 |
| ② 공급 입고 | AJ | AJ가 EDI에 등록 | 렌탈입고(AJ센터 → 우리) | 요청 대비 실입고 대조, 부족·지연 알림 |
| ③ 출고·이동·반납 | 우리 작업자 | PMS(사진·서명) → EDI 자동입력 | 이동출고 | 등록, EDI 반영 확인(이동코드 연결) |

- **로그인 아이디**: 현장·시공팀은 이메일이 없는 경우가 많아 **휴대폰 번호를 아이디로**(내부적으로 `010xxxxxxxx@letus.pms` 같은 형태) + 관리자가 임시 비밀번호 발급 → 첫 로그인 때 변경. (SMS 인증은 비용이 들어 2단계에서 검토)
- **역할 이름 정리**: 지금의 "협력업체" → "시공팀"으로 바꾸고, "운송팀(센터 지정)"을 "센터 작업자"로 분리해 화면·권한을 단순하게.
- **퇴사·교체**: 계정 비활성화(이미 있음) + 전표에 작업자 이름이 남으니 기록은 유지.
- **처음 운영**: 관리자 2 + 운송팀 3 + 양지계열 센터 작업자 각 2 + 시공팀 상위 10팀 → 2주 써 보고 확대.

### EDI 계정 (회사 단위 3개, 사람이 공유)
- 로그인 3개(14C·18F / 일반유형 / 23E), 계정당 동시 접속 1개, SMS 인증이 한 휴대폰으로 감.
- **권장 운영**: EDI에 직접 들어가는 사람은 **EDI 담당 1~2명**으로 한정. Chrome 프로필 3개(계정별)에 각각 로그인해 두고 동기화·[저장]·[입고확인]은 이 사람만. 나머지는 PMS만 사용.
- PMS가 대신하는 것: 출고 입력(자동입력), 납품요청(채우기), 입고확인 판단, 재고·정산 조회 → **현장 인원은 EDI 계정이 필요 없어요.**
- EDI 납품요청 목록의 등록자(INST_EMPN)에 "김민지", "웹마스터" 등 사람 이름이 섞여 있어, EDI도 회사 안에 사용자 구분이 있는 것으로 보임 → AJ에 **사용자별 하위 계정·SMS 수신 번호 변경** 가능 여부 문의.

## 12. AJ 미팅 안건 (추가분, 2026-10-28)
1. **18F 공급률**: 10월 납품요청 대비 렌탈입고 18F 34~46%(충주1 3,040 → 1,025), 14C 95~100%. 18F 물량 부족 여부, 앞으로 공급 계획.
2. **납품요청 '완료' 처리 기준**: 덜 보내도 완료로 닫힘 → 부분 납품이면 '부분완료'와 잔량 표시, 잔량 자동 이월 여부.
3. **렌탈입고(D)·반납출고(S)에 요청코드(C) 연결**: 지금은 작업장·제품·희망일로 맞춤(10/01~ 47줄 1:1). 같은 날 같은 곳에 요청이 둘이면 구분 불가.
4. **회수요청 전산화**: EDI에 회수요청 메뉴가 없음(전화·배차). 요청·배차·실회수를 EDI에서 볼 수 있게.
5. **렌탈입고 수량 상이 처리**: 우리가 EDI에서 못 고침 → 수정요청 게시판으로 올리는 방식이 맞는지, 처리 기한.
6. 렌탈입고가 대부분 '수정'되는 이유와 확정 시점.
7. EDI 이동등록·입고확인 마감 운영(지금 한 번도 설정 안 됨) — 정산 기준일과 맞출지.
8. 사용자별 하위 계정·SMS 수신 번호 변경 가능 여부.
