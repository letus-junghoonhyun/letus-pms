> 기준일 2026-10-28. 지금까지 논의를 바탕으로, 질문이 여러 번 바뀐 것은 **가장 최근 결정**으로 정리했어요.
> 자세한 EDI 분석 수치는 `docs/EDI_구조분석_PMS_재정비.md`, 예전 방향 문서는 `docs/PMS_고도화_방향.md`.

## 1. 무엇을 만드는가

**목표**: 옛 파렛트 앱을 대신해, AJ EDI(edi.ajuprs.com)를 **장부**로 두고 PMS가 현장 작업(출고·입고 확인·AJ 요청·상이 처리)을 쉽게 만들어 **EDI 재고 = PMS 재고 = 실물**이 계속 맞게 가는 것.

**대원칙 (정훈님 결정, 10-28)**
- EDI와 PMS 재고는 **무조건 같아야** 한다. PMS의 모든 작업은 그 일치에 의미가 있어야 한다.
- PMS는 별도 재고 장부를 두지 않는다. **재고 = EDI 마지막 재고일 재고 + 그 뒤 EDI 이동(오늘까지)**.
- 입고확인 여부와 관계없이 EDI 이동이 올라오는 순간 보낸 곳 −, 받는 곳 + (EDI 재고조회와 같은 방식). EDI의 "확인재고"는 입고확인분만 따로 센 값.

**기술 구성**: React(Vite) 한 파일 `src/App.jsx` · Supabase(DB·인증·함수 `edi-ingest`) · Vercel 자동 배포(letus-pms.vercel.app) · EDI 연동은 Tampermonkey 스크립트 `tools/edi-sync.user.js`(로그인된 Chrome 안에서 동작).

## 2. 왜 이렇게 설계했나 — 문제와 결정

| # | 문제 | 결정 |
|---|---|---|
| 1 | EDI 로그인에 휴대폰 문자 인증 → 서버가 혼자 로그인 불가 | 로그인된 Chrome 안의 스크립트가 동기화·자동입력. 사람은 로그인과 마지막 [저장]만. 30분마다 오늘 이동 재수집(v3.18). 근본 해결은 AJ 정식 연동 요청 |
| 2 | EDI 계정 3개(14C·18F / 일반유형 11A·15A / 23E), 계정마다 따로 로그인 | 스크립트가 로그인 계정을 자동 인식, 계정별로 저장. EDI에 들어가는 사람은 담당 1~2명 |
| 3 | 출고를 방향(출고/반납/이동)별로 따로 입력 → 헷갈림 | **출고처 → 입고처 한 양식**으로 통일. 바꾸기 버튼 없음(반납도 현장이 출고처) |
| 4 | EDI 저장을 PMS가 대신 눌러도 되나 | AJ 합의 전까지 **채우기만** 하고 [저장]은 사람이. 합의 후 설정으로 켜기 |
| 5 | 받는 쪽이 입고확인을 거의 안 함(7%) | PMS **입고 확인** 화면: [정상]/[상이]. 다음날 지나면 자동확인 |
| 6 | 자동확인을 EDI에 보낼지 | 기본 **안 보냄**(`auto_conf_to_edi=N`). [정상] 누른 것만 EDI 입고확인 대기. 지난 미확인 4,777건은 보류(마감 때 정리) |
| 7 | 실제 수량이 다를 때 누가 고치나 | [상이] → 수정요청 → 관리자 승인(=협의 완료) → 보낸 곳에 따라 3경로 (5장) |
| 8 | AJ 납품요청과 실제 입고가 EDI에서 연결 안 됨 | 규칙 매칭: 같은 계정+작업장+제품+**렌탈입고일=희망일** (10/01~ 47줄 전부 1:1). 실입고는 **받는 쪽 확인 수량** 기준 |
| 9 | AJ는 덜 보내도 납품요청을 '완료'로 닫음 (18F 34~46%) | 공급 현황에 "덜 들어옴" 표시. 재요청/종결 버튼은 두지 않음(정보만) — 필요하면 평소처럼 새로 요청 |
| 10 | 회수는 EDI에 요청 메뉴가 없음 | PMS 회수 요청 ↔ EDI 반납출고(S코드) 매칭. 목적: 가져가 달라고 한 만큼 실제로 나갔나(임차료) |
| 11 | 시공팀은 EDI에서 보내는 쪽으로 0건 (반납 미기록) | **핵심 수불 구멍.** 시공팀이 PMS에서 자기 현장 출고(반납) 등록 → EDI 이동으로 연결 |
| 12 | 업체는 PMS를 안 쓸 것 | 업체 계정 없음. 업체 쪽 흐름은 EDI 데이터로 본다 |
| 13 | 저장소 공개 여부 | 공개 유지(회사 내부 서버로 이전 예정) |
| 14 | 출고 받는 곳에 EDI 업체가 다 안 나옴 | 받는 곳 = 우리 작업장 500 + **EDI 입고처 1,231곳**(쿠팡 센터 등) 추가(10-28) |

## 3. EDI 구조 요약 (읽기 전용 분석 결과)

- **이동조회/관리** `WARE_MOVE_LIST`: 위 기준칸(flag)을 **실착지**로 바꿔야 [입고확인]·[승인거부]가 보임. 입고확인 `EDI_WARE_MOVE_CONF_UPDT.do`, 승인거부 `EDI_WARE_MOVE_LIST_APPR.do`(사유 01 전표없음 / 02 수량불일치 / 03 기타), 수량 수정 `EDI_WARE_MOVE_LIST_SAVE.do`.
- **이동등록(추가)** `WARE_MOVE_DETL`: [업로드]가 등록용. 허용 입고처는 출고처마다 다름.
- **납품요청/조회** `OTHR_SIGN_LIST`: 16시 마감(다음날 희망), 토요일 영업일, 공휴일 불가, 처리중 전까지 수정·삭제.
- **수정요청 게시판** `OTHR_UPDT_DETL`: AJ 공급(D)·회수(S) 건 정정은 여기로만.
- 이동코드: **M 이동 / D 렌탈입고(AJ 공급) / S 반납출고(AJ 회수)**. D·S는 이동조회/관리에 안 나옴.
- EDI 마감이 한 번도 설정된 적 없음 → 지난 이동도 언제든 고칠 수 있음.
- 마이너스 재고 존재: 예) 에픽 18F −934(10월 입 601 / 출 1,229), 양지2센터 14C −1,978 → **기록 없이 들어오는 파렛트**가 있다는 뜻(7장 과제).

## 5. 상이(수량 다름) 처리 경로

받는 쪽 [상이] → 실제 받은 수량·사진 → 관리자 [승인](=협의 완료) → 보낸 곳에 따라:

| 보낸 곳 | EDI 처리 | 누가 최종 수정 |
|---|---|---|
| 우리 작업장끼리 | 이동조회/관리에서 수량 수정 (스크립트가 채움) | 우리 |
| 다른 업체 | 받는 쪽 기준 **승인거부(02 수량불일치)** + 실제 수량 비고 | 그 업체가 상이내역 회신에서 |
| AJ 공급·회수(D/S) | AJ 수정요청 게시판에 정정 요청 | AJ |

**자동 반영 여부**: 기술적으로 승인 → EDI 자동 저장 가능. AJ 합의 후 설정(기본 끔)으로 켤 예정.

## 6. 계정 관리안 (10-28 최신)

**업체 제외, 센터 + 시공팀 + 내부**로 시작.

| 역할 | 누구 | 범위 | 할 수 있는 것 |
|---|---|---|---|
| 관리자 | 운송사업팀 담당 2~3명 | 전체 | 승인, 마감, 단가, 사용자, 설정 |
| 운송팀(현장 담당) | 3~5명 | 전체 작업장 | 출고·입고확인·EDI 반영·AJ 요청 |
| **센터 작업자** | 활동 센터 19곳 × 1~3명 | **연결된 센터 작업장만**(여러 곳 가능) | 내 센터 출고·입고확인 |
| **시공팀** | 팀장 1명(활동 31팀, 상위 10팀부터) | **연결된 자기 현장 작업장만** | 자기 현장 입고확인, 자기 현장에서 보내기(반납 포함) |
| 정산담당 | 1~2명 | 재고·정산·EDI | 정산서 |

- **연결 방식**: 사람 계정 ↔ EDI 작업장(aj_workplace)을 관리자가 연결. 센터 작업자는 여러 작업장, 시공팀은 자기 팀 현장 작업장(들).
- 아이디: 현장·시공팀은 **휴대폰 번호**(내부 `010…@letus.pms`) + 관리자가 임시 비밀번호 → 첫 로그인 때 변경.
- 역할 이름: "협력업체" → **"시공팀"**, 운송팀(센터 지정) → **"센터 작업자"**로 분리.
- EDI 계정은 회사 단위 3개, EDI 담당 1~2명만 로그인(Chrome 프로필 3개). 현장 인원은 EDI 계정 불필요.

## 7. 남은 과제

### 실전 투입 전 (P1)
1. **계정 구조 반영**: 센터 작업자 역할 신설, 협력업체→시공팀, 사람↔작업장 연결 화면
2. **실전 테스트** (8장)
3. **전표 양식 방향 결정** (9장) — 정훈님이 쿠팡·브랜드 확인 후
4. **마이너스 재고 점검 화면**: 기록 없이 들어오는 곳 찾기(에픽, 양지2센터 등)
5. 23E 계정 이동 0건 확인(정훈님 EDI 화면 확인: 이동 없음 → 정상)
6. 실사용자 등록 → 2주 시범(관리자 2 + 운송팀 3 + 양지계열 센터 작업자 + 시공팀 상위 10팀)

### 운영하면서 (P2)
- EDI 시점 측정: AJ가 실물보다 먼저 EDI에 올리는지 (`aj_move.first_seen` vs 입고 확인 시각) — 동기화 자주 하면서 데이터 쌓는 중
- 실사 1회로 EDI·PMS·실물 맞추기, 이후 월 마감 운영
- 지난 미확인(보류) 정리 기준 정하기

### 장기 (P3)
- 운영환경: 회사 내부 서버 이전(Supabase 유료 대비)
- AJ 정식 연동(조회 API·인증 없는 연동 계정)

### AJ 미팅 안건
18F 공급률 / '완료' 처리 기준 / D·S코드에 요청코드 연결 / 회수요청 전산화 / 렌탈입고 상이 처리 기한 / 렌탈입고 '수정' 이유 / EDI 마감 운영 / 사용자별 하위 계정·SMS 번호 / **PMS 자동 저장 허용 여부** / **전표 양식 일원화** / 정식 연동

## 8. 실전 투입 전 테스트 계획

원칙: 실제 EDI에 쓰되, **우리 작업장끼리 소량(1장)**으로 하고 끝나면 **수량 0으로 고쳐** 원상복구. 테스트 건 비고에 "PMS 테스트".

| # | 시나리오 | 확인할 것 |
|---|---|---|
| 1 | 출고 등록(양지물류센터 → 양지2센터, 18F 1장) → EDI 자동입력 → [저장] | EDI 이동코드가 PMS에 연결, 오늘 할 일 "EDI 미반영"에서 빠짐 |

| 4 | 외부 입고처(쿠팡 센터 등)로 출고 등록 → 자동입력까지만(저장 안 함) | 입고처 코드가 맞게 채워지는지 |
| 5 | AJ 납품요청 채우기(저장 안 함) | 16시 규칙·최소수량·희망일 |
| 6 | 시공팀 계정으로 로그인 → 자기 현장만 보이는지, 반납 등록 | 권한 범위 |
| 7 | 센터 작업자 계정 → 다른 센터가 안 보이는지 | 권한 범위 |
| 8 | 휴대폰에서 입고 확인(사진·QR) | 화면 크기·속도 |
| 9 | 지도·재고: 테스트 후 해당 작업장 수량이 EDI와 같은지 | 일치 |

## 9. 전표 양식

- **AJ EDI 전표**(파렛트 이동전표 4매: 발송처·파렛트회사·운송회사·도착처용): 위 바코드 = **EDI 전표번호(MOVE_BILL)**, 아래 = 계정-작업장. 바코드 스캔 모드로 EDI 입고확인하는 곳(쿠팡 등)은 이 번호를 씀.
- **PMS 전표**(4매: 발송처·도착처·운송회사·보관용): 차량정보·용도·상태 체크(정상/파손/수량상이)·출고확인/운송/인수 서명 — 현장용으로 더 좋음.
- 결정 포인트: 받는 곳이 AJ 바코드를 스캔해서 입고확인한다면 PMS 전표에도 **EDI 전표번호 바코드**가 있어야 함 → EDI [저장] 후 번호가 생기므로 "저장 → PMS 전표 인쇄" 순서. 정훈님이 쿠팡·브랜드 확인 후 (a) PMS 양식 + EDI 번호 바코드 / (b) AJ 양식 그대로 / (c) AJ와 일원화 중 결정.
